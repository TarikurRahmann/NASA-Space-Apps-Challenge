# Project Pitch and Demo Guide
## NASA Space Apps Challenge-এর জন্য project বোঝানো, demo সাজানো ও প্রশ্নের উত্তর

> **এটি presentation প্রস্তুতির সহায়ক guide—NASA-র official judging rubric বা নির্দিষ্ট বছরের pitch-duration requirement নয়।** আপনার Local Event, Global Judging বা submission-এর জন্য নির্দিষ্ট সময়, format, media, language বা প্রশ্নোত্তরের নিয়ম থাকলে current-year event page, Project Submission Guide ও Judging & Awards Guide-ই অনুসরণ করুন।
>
> নিচের ৩০-সেকেন্ড, ৯০-সেকেন্ড ও ৩-মিনিটের structure-গুলো practice template। এগুলো বাধ্যতামূলক সময়সীমা নয় এবং award পাওয়ার নিশ্চয়তা দেয় না।

## ১. ভালো pitch-এর লক্ষ্য

Pitch-এর লক্ষ্য সব feature-এর তালিকা পড়ে শোনানো নয়। শ্রোতাকে দ্রুত বুঝতে সাহায্য করুন:

1. কোন problem বা challenge নিয়ে কাজ করেছেন;
2. কার জন্য solution;
3. NASA বা অন্য permitted source-এর কোন data/resource ব্যবহার করেছেন;
4. Project কী করে—live demo বা নির্দিষ্ট evidence-সহ;
5. কী পরীক্ষা করেছেন এবং ফলের সীমা কোথায়।

একটি পরিষ্কার pitch সাধারণত এই flow-তে যায়:

```text
Problem → User → Insight/data → Solution → Demo → Evidence → Limitation/next step
```

এই order প্রয়োজন অনুযায়ী বদলাতে পারেন। Challenge statement ও presentation prompt-এর required বিষয় যেন বাদ না যায়।

## ২. Pitch-এর আগে official requirement যাচাই

প্রস্তুতির আগে জেনে নিন:

- presentation-এর সময় কত;
- live demo, recorded video, slide বা prototype দেখাতে হবে কি না;
- team-এর কয়জন উপস্থাপন করতে পারবেন;
- প্রশ্নোত্তরের সময় বা ভাষা-সংক্রান্ত শর্ত আছে কি না;
- presentation onsite নাকি virtual;
- external link বা account খুলে দেখানো অনুমোদিত কি না;
- judging-এর criteria কী এবং কোন guide-এ দেওয়া;
- project-এর কোন তথ্য/field submission-এর সঙ্গে মিলতে হবে।

এগুলো বছর, event ও judging stage অনুযায়ী বদলাতে পারে। এখানে কোনো নির্দিষ্ট format-কে NASA-র সার্বজনীন নিয়ম বলা হচ্ছে না।

## ৩. শ্রোতা ও message নির্ধারণ

Presentation লেখার আগে team মিলে এই বাক্যগুলো পূরণ করুন:

```text
আমরা যে challenge/problem address করেছি:
আমাদের প্রধান user/audience:
User-এর যে কাজটি কঠিন:
আমাদের solution user-কে যা করতে/বুঝতে সাহায্য করে:
আমাদের সবচেয়ে গুরুত্বপূর্ণ evidence:
আমাদের সবচেয়ে বড় limitation:
```

### One-line project description

এই template ব্যবহার করে একটি বাক্য লিখুন:

> “[ব্যবহারকারী]-কে [সমস্যা/কাজ]-এ সাহায্য করতে আমরা [solution] তৈরি করেছি, যা [প্রাসঙ্গিক data/পদ্ধতি] ব্যবহার করে [দেখানো যায় এমন ফল] দেয়।”

বাক্যটি যেন:

- challenge ও intended user-এর সঙ্গে মেলে;
- project বাস্তবে যা করে, শুধু সেটিই বলে;
- “revolutionary”, “perfect”, “100% accurate” বা প্রমাণহীন দাবি এড়িয়ে চলে;
- technical jargon-এ ভরা না হয়।

## ৪. ৩০-সেকেন্ডের pitch template

সময় কম হলে এই ৪ অংশে বলুন:

1. **Problem:** “আমরা [challenge/problem] নিয়ে কাজ করেছি।”
2. **User:** “এটি [user]-কে [কাজে] সাহায্য করে।”
3. **Solution/data:** “আমরা [solution] তৈরি করেছি, যেখানে [data/source] ব্যবহার হয়েছে।”
4. **Proof/limit:** “Demo-তে [একটি ফল] দেখাব; এটি বর্তমানে [একটি গুরুত্বপূর্ণ limitation]-সহ prototype।”

### নমুনা কাঠামো—নিজের project অনুযায়ী পূরণ করুন

```text
আমরা [সমস্যা] নিয়ে কাজ করেছি, যা [ব্যবহারকারী]-এর জন্য [কেন গুরুত্বপূর্ণ]।
আমাদের [project name] [নির্দিষ্ট কাজ] করতে সাহায্য করে।
এতে আমরা [officially verified data/source] ব্যবহার করেছি।
এখন দেখাব [একটি main action/result]। এটি prototype; [limit/assumption] এখনও যাচাই প্রয়োজন।
```

## ৫. ৯০-সেকেন্ডের pitch structure

| সময়ের আনুমানিক অংশ | কী বলবেন | কী দেখাবেন |
|---|---|---|
| ০–১৫ সেকেন্ড | Challenge ও user problem | Title + problem-এর একটি সহজ visual |
| ১৫–৩০ সেকেন্ড | User-এর প্রয়োজন; কেন সমাধান দরকার | User journey বা context |
| ৩০–৪৫ সেকেন্ড | Data/source ও আপনার insight | Dataset/variable-এর সংক্ষিপ্ত পরিচয় |
| ৪৫–৭০ সেকেন্ড | Solution-এর core flow | একটি end-to-end live/demo path |
| ৭০–৮২ সেকেন্ড | Test/evidence, limitation | Test result বা স্পষ্ট caveat |
| ৮২–৯০ সেকেন্ড | Takeaway/next step | একটি সংক্ষিপ্ত closing sentence |

সময় নিজের event-এর নির্দেশনা অনুযায়ী adjust করুন। Demo যদি ধীর হয়, intro ছোট করে core interaction-এ সময় দিন।

## ৬. ৩-মিনিটের pitch structure

এই outline-টি ৩ মিনিটের উদাহরণ; required duration নয়।

### ০:০০–০:২০ — Hook ও problem

- বাস্তব user question বা একটি নির্দিষ্ট পরিস্থিতি দিয়ে শুরু করুন;
- problem-টি challenge-এর সঙ্গে যুক্ত করুন;
- অপ্রমাণিত ভয় বা নাটকীয় দাবি দিয়ে শুরু করবেন না।

### ০:২০–০:৪৫ — User ও প্রয়োজন

- কাদের জন্য project;
- তাদের কী জানতে/করতে হয়;
- বর্তমানে কোন বাধা বা তথ্যের ঘাটতি আছে—যদি evidence থাকে।

### ০:৪৫–১:১০ — Data ও পদ্ধতি

- কোন dataset/API/mission/resource ব্যবহার;
- project-এর জন্য কোন variable/observation প্রাসঙ্গিক;
- data কীভাবে filter/process/visualize করেছেন—প্রয়োজনমতো।

শুধু source-এর নাম বলে থেমে যাবেন না; data project-এর প্রশ্নের সঙ্গে কীভাবে মেলে, সেটিও বলুন।

### ১:১০–২:১০ — Demo

- User কী input দেবে;
- Project কী দেখাবে;
- Output কীভাবে user-এর প্রশ্নে সাহায্য করবে;
- main path-এ থাকা feature-গুলোই দেখান।

### ২:১০–২:৩৫ — Test ও evidence

- কোন sample/test case দিয়ে core flow যাচাই;
- ফলটি কী বোঝায়;
- Data বা prototype-এ কী uncertainty/limitation আছে।

### ২:৩৫–২:৫০ — Impact ও next step

- এই project কোথায় উপকারী হতে পারে—প্রমাণের সীমা মেনে;
- পরের iteration-এ কী data, test বা feature দরকার।

### ২:৫০–৩:০০ — Closing

একটি বাক্যে project ও takeaway পুনরাবৃত্তি করুন। “সব সমস্যার সমাধান” বা award-এর প্রতিশ্রুতি দেবেন না।

## ৭. Slide বা visual narrative

যদি slide ব্যবহার করার অনুমতি/প্রয়োজন থাকে, অল্প কিছু slide-এ message সাজান। Slide-এর সংখ্যা এখানে নির্ধারিত নয়—সময় ও official instruction অনুযায়ী ঠিক করুন।

### সম্ভাব্য slide sequence

1. **Title:** Project name, team ও selected challenge;
2. **Problem/user:** কাকে কী সমস্যা থেকে সাহায্য করতে চান;
3. **Data/insight:** source ও relevant observation;
4. **Solution:** user flow বা system diagram;
5. **Demo/evidence:** prototype ও test result;
6. **Limitations/next step:** কী জানা নেই, এরপর কী করা দরকার।

### Visual check

- প্রতি slide-এ একটি প্রধান idea;
- ছোট font ও দীর্ঘ paragraph এড়িয়ে চলুন;
- chart-এ title, axis, unit, date range, legend ও source দিন;
- colour-only encoding হলে বিকল্প label/shape যোগ করুন;
- map-এ scale, projection/context ও source উল্লেখ করুন—প্রাসঙ্গিক হলে;
- screenshot-এর text readable কি না presentation view-তে পরীক্ষা;
- data-র scale বা crop এমনভাবে বদলাবেন না যাতে ভুল ধারণা হয়;
- image/media-র source, credit ও usage permission যাচাই করুন;
- slide-এ API key, password, email, personal information বা confidential data নেই।

## ৮. Live demo পরিকল্পনা

### ৮.১ Demo-তে একটিই main journey বেছে নিন

Demo-র জন্য এমন একটি path নিন যা সবচেয়ে পরিষ্কারভাবে challenge-এর core problem-এর উত্তর দেখায়:

```text
শুরু → একটি user action/input → processing/data view → ফলাফল → ব্যাখ্যা
```

সব menu, setting ও feature দেখানোর চেষ্টা করবেন না। একটি সম্পূর্ণ user journey কয়েকটি অসম্পূর্ণ feature tour-এর চেয়ে বেশি বোধগম্য।

### ৮.২ Demo runbook

```text
Demo owner:
Backup presenter:
Starting URL/file:
Starting state/account:
Input/sample:
Step 1:
Step 2:
Step 3:
Expected result:
কোন data/source mention করব:
Known limitation:
Internet/API fallback:
Screenshot/video/local fallback:
শেষের transition/closing:
```

### ৮.৩ Demo environment প্রস্তুত

- [ ] প্রয়োজনীয় app/page আগে খুলে রাখুন।
- [ ] Demo account, sample input ও test location/date প্রস্তুত।
- [ ] Browser tab/notification/private message/credential দেখানো হবে না—যাচাই।
- [ ] প্রয়োজনীয় file offline-এ রাখা যাবে কি না current rules অনুযায়ী দেখুন।
- [ ] Network/API বন্ধ হলে কোন screenshot, local sample বা recorded backup দেখাবেন স্থির।
- [ ] Demo data real, sample, synthetic বা cached—যা-ই হোক, সত্যভাবে label।
- [ ] Project link reviewer-এর access আছে কি না অন্য account/device থেকে পরীক্ষা।
- [ ] Demo-র প্রতিটি ধাপের আনুমানিক সময় মেপে দেখুন।
- [ ] Presenter ভুল click করলে দ্রুত ফিরে আসার reset/restart path জানেন।

### ৮.৪ Live failure হলে

শান্তভাবে failure স্বীকার করুন; বারবার reload করে পুরো সময় ব্যয় করবেন না।

1. কী ব্যর্থ হয়েছে এক বাক্যে বলুন (যেমন network/API response);
2. Feature-এর intended behavior ব্যাখ্যা করুন, তবে কাজ করছে বলে দাবি করবেন না;
3. প্রস্তুত fallback চালান;
4. Fallbackটি screenshot, local sample বা recorded demo—যা, তা স্পষ্ট করুন;
5. Failure-এর কারণে ফল যাচাই হয়নি—এ কথা দরকার হলে বলুন।

## ৯. Demo rehearsal

### Rehearsal 1 — Flow

- Project explanation থেকে demo-তে যাওয়া স্বাভাবিক কি?
- Presenter input ও expected result জানেন?
- Demo-র central user question-এর উত্তর পাওয়া যায়?

### Rehearsal 2 — Timing

- নিজের event-এর নির্দিষ্ট duration মানুন;
- দ্রুত বলার কারণে গুরুত্বপূর্ণ limitation বা source বাদ পড়ছে কি না দেখুন;
- demo ধীর হলে intro/feature কমান, কথা আরও দ্রুত করবেন না।

### Rehearsal 3 — Failure/fallback

- Internet/API unavailable ধরে fallback চালান;
- Link না খুললে কীভাবে screenshot/video/local sample দেখাবেন;
- Presenter-এর laptop/account failure হলে backup কে চালাতে পারেন?

### Rehearsal 4 — Outside listener

যিনি project বানাননি এমন কাউকে pitch শোনান। তাঁকে জিজ্ঞেস করুন:

- Project কোন সমস্যার সমাধান করে?
- কার জন্য?
- Data/source কী ভূমিকা রেখেছে?
- Demo-তে কী কাজ করতে দেখলেন?
- কোন দাবি বা শব্দ বুঝতে অসুবিধা হয়েছে?
- Project কী করতে পারে না—তা কি স্পষ্ট?

## ১০. Team speaking roles

একাধিক সদস্য বললে transition আগে practice করুন। প্রত্যেকে নির্দিষ্ট অংশ বলবেন, তবে পুরো project-এর ওপর team-এর সবাইকে মৌলিক প্রশ্নের উত্তর দিতে প্রস্তুত থাকতে হবে।

| Speaker | সম্ভাব্য অংশ | Handoff |
|---|---|---|
| Speaker 1 | Problem, user, challenge fit | “এবার [নাম] data ও approach দেখাবে।” |
| Speaker 2 | Data, method ও limitation | “এখন [নাম] prototype-এ এই flow দেখাবে।” |
| Speaker 3 | Demo ও test evidence | “শেষে [নাম] next step ও limitation সংক্ষেপ করবে।” |
| Speaker 4 (যদি থাকে) | Validation, impact, next step | প্রশ্নোত্তরের জন্য transition |

এটি শুধু উদাহরণ। Team member-এর contribution ভুলভাবে বড়/ছোট করে দেখাবেন না; কে কী করেছে তা সঠিকভাবে স্বীকার করুন।

## ১১. প্রশ্নোত্তরের প্রস্তুতি

প্রশ্নের উত্তর দেওয়ার সহজ পদ্ধতি:

```text
প্রশ্ন শুনুন → মূল বিষয় পরিষ্কার করুন → সংক্ষিপ্ত উত্তর দিন
→ প্রয়োজন হলে evidence/assumption বলুন → limitation স্বীকার করুন
```

### উত্তর দেওয়ার নিয়ম

- প্রশ্ন শেষ হওয়ার আগে বাধা দেবেন না।
- প্রশ্ন অস্পষ্ট হলে বিনয়ের সঙ্গে নির্দিষ্ট অংশ জানতে চান।
- সংক্ষিপ্ত উত্তর আগে দিন; তারপর প্রয়োজনীয় ব্যাখ্যা।
- যা জানেন না, বানিয়ে বলবেন না।
- Data/source, method, test ও limitation-এর মধ্যে কোনটির ওপর উত্তর দাঁড়ানো—তা স্পষ্ট করুন।
- “আমরা যাচাই করিনি” বলা, অনুমানকে fact হিসেবে বলার চেয়ে ভালো।
- Team member-এর জানা বিষয় হলে তাঁকে উত্তর দিতে দিন।

### সম্ভাব্য প্রশ্ন ও প্রস্তুতির দিক

#### “কেন এই challenge বেছে নিলেন?”

- Problem/user কীভাবে বুঝেছেন;
- Team-এর skill ও আগ্রহের সঙ্গে fit;
- MVP-তে challenge-এর কোন requirement address।

#### “কোন NASA data ব্যবহার করেছেন?”

- Dataset/collection, provider, version/date range;
- কী variable ব্যবহার;
- কেন এটি user question-এর জন্য প্রাসঙ্গিক;
- citation ও licence কোথায় আছে।

#### “Data কতটা accurate?”

- Product documentation/quality flag কী বলে;
- Team কী পরীক্ষা করেছে;
- কোন uncertainty বা limitation বাকি;
- evidence-এর বাইরে accuracy number দাবি করবেন না।

#### “কেন এই method/model?”

- সহজ ভাষায় method-এর কাজ;
- কোন input ও assumption;
- কীভাবে test/compare করেছেন;
- method-এর known failure mode।

#### “এটি real-world-এ ব্যবহার করা যাবে?”

- Prototype-এর বর্তমান অবস্থা;
- real deployment-এর আগে প্রয়োজনীয় validation, data, safety review বা user testing;
- বর্তমান project কী প্রমাণ করেছে আর কী করেনি।

#### “AI/SI ব্যবহার করেছেন?”

- Current-year rule অনুযায়ী সত্য উত্তর;
- কোন tool কোন কাজে ব্যবহার;
- team কীভাবে output যাচাই/সম্পাদনা করেছে;
- submission-এ disclosure কোথায় দেওয়া।

#### “পরের ধাপে কী করবেন?”

- সবচেয়ে জরুরি data/validation;
- user feedback বা reliability improvement;
- একটি পরিমাপযোগ্য next milestone।

#### “এই ফল অন্য region/time-এও প্রযোজ্য?”

- Data coverage ও model validation কতদূর;
- tested region/time range;
- generalization করতে কী পরীক্ষা বাকি।

### “জানি না” বলার ভালো পদ্ধতি

```text
“এটি আমরা সরাসরি পরীক্ষা করিনি, তাই নিশ্চিতভাবে বলতে পারছি না।
এখন পর্যন্ত আমাদের evidence হলো [যা পরীক্ষা হয়েছে]।
পরের ধাপে আমরা [যে পরীক্ষা/ডেটা দরকার] দিয়ে বিষয়টি যাচাই করব।”
```

এটি দুর্বল উত্তর নয়; evidence ও limitation সৎভাবে দেখায়।

## ১২. Judging সম্পর্কে সতর্কতা

- আপনার বছরের Judging & Awards Guide-এ criteria/format থাকলে তা পড়ুন।
- কোনো পুরোনো blog, আগের বছরের score বা অন্য team-এর অনুমানকে current rubric হিসেবে ধরবেন না।
- এই guide-এর pitch outline, demo rehearsal বা slide order NASA judging criteria নয়।
- Award, nominee status বা score নিশ্চিত—এমন ভাষা ব্যবহার করবেন না।
- Project-এর সৌন্দর্য/feature count-এর চেয়ে challenge fit, কাজের evidence ও সঠিক ব্যাখ্যা গুরুত্বপূর্ণ—তবে সুনির্দিষ্ট মূল্যায়ন current rubric-ই নির্ধারণ করে।

## ১৩. Presentation-এর ভাষা ও accessibility

- Technical term প্রথমবার এলে সহজ ব্যাখ্যা দিন।
- Acronym কম ব্যবহার করুন; দরকার হলে পূর্ণরূপ বলুন।
- ছোট বাক্য ও স্পষ্ট verb ব্যবহার করুন।
- Chart-এর colour, label ও contrast এমন রাখুন যাতে বোঝা যায়।
- শুধু রং দিয়ে পার্থক্য বোঝাবেন না—text/shape/legend যোগ করুন।
- Video থাকলে caption/subtitle/transcript প্রযোজ্য কি না দেখুন।
- Audience-এর expertise না জেনে অতিরিক্ত jargon ব্যবহার করবেন না।
- অন্য ভাষায় presentation হলে নাম, unit ও data term-এর উচ্চারণ/লিখন practice করুন।

## ১৪. Pitch readiness checklist

### Content

- [ ] Pitch-এ challenge ও problem স্পষ্ট।
- [ ] Target user ও user need বোঝা যায়।
- [ ] NASA/other source-এর data কীভাবে ব্যবহৃত হয়েছে বলা আছে।
- [ ] Solution-এর core capability বলা ও দেখানো হয়।
- [ ] Claim evidence দিয়ে সমর্থিত।
- [ ] Limitation, uncertainty ও অসম্পূর্ণতা সৎভাবে উল্লেখ।
- [ ] Current guide-এর presentation format ও timing মেনে চলে।

### Demo

- [ ] একটি main user journey নির্বাচিত।
- [ ] Demo-র input ও expected output প্রস্তুত।
- [ ] Live link/account/permission পরীক্ষা।
- [ ] Network/API failure-এর fallback প্রস্তুত।
- [ ] Mock/synthetic/cached data থাকলে স্পষ্ট label।
- [ ] Demo-তে secret, personal বা confidential তথ্য নেই।
- [ ] Demo-র সময় মেপে practice করা হয়েছে।

### Team

- [ ] Speaker-দের অংশ ও transition পরিষ্কার।
- [ ] প্রতিটি সদস্য নিজের contribution সঠিকভাবে বর্ণনা করতে পারেন।
- [ ] প্রশ্নের উত্তর না জানলে কীভাবে evidence/limitation বলবেন জানেন।
- [ ] Q&A-এর আগে কে উত্তর দেবেন এবং কাকে handoff করবেন ঠিক।
